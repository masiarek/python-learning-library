# Defining `__eq__` deletes `__hash__`

**Level:** 301 · for Python programmers

**One line:** A class that defines `__eq__` and not `__hash__` gets `__hash__ = None` and becomes unhashable, because equal objects must hash equal and Python would rather refuse than let a set hold two copies of one value — so a `@dataclass` is unhashable unless it is frozen, and an object whose fields change while it sits in a set is lost until they change back.

```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)

Point.__hash__      # None
{Point(1, 2)}       # TypeError
```

A dict and a set find a key by its hash first and confirm it with `==` second, so the two methods have to agree: whenever `a == b`, `hash(a)` must equal `hash(b)`. `object` keeps that promise trivially, with an `__eq__` that means *same object* and a hash derived from identity. The moment a class says that two different objects are equal, the inherited identity hash breaks the promise, and rather than leave a class in that state the `class` statement sets `__hash__` to `None`. That is a refusal, not an oversight: the class is unusable as a key until someone says what its hash is.

The other half of the page is what the promise costs once it is kept. A hash computed from fields is only right while the fields hold still, and Python does not stop a hashable object from changing.

## What the run shows

**Section 1: a class with neither method.** Two `Point(1, 2)` objects are not `==`, because `object.__eq__` means identity, and `len({p, q})` is `2`, because each hashes by identity. Consistent, and useless for a value type.

**Section 2: define `__eq__`, and `__hash__` is gone.** With an `__eq__` that compares fields, `p == q` is `True` and `Point.__hash__` is `None`. `hash(p)` raises `TypeError`, and so does `{p, q}`: no set member and no dict key. Nothing in the class body mentioned `__hash__`; the class statement did this on its own.

**Section 3: why.** `Bad` puts the identity hash back beside the value `__eq__`, which is what the class in section 2 would have been without the rule. `p == q` is `True`, and `len({p, q})` is `2` anyway: two equal members in one set. `q in {p}` is `False`, because the lookup computes `hash(q)`, goes where that hash points, and finds nothing there. Equality that the containers cannot see is the state the rule exists to prevent.

**Section 4: the fix.** A `__hash__` built from the same fields `__eq__` compares restores the promise: `len({p, q})` is `1`, `q in {p}` is `True`, and `{p: 'here'}[q]` finds `p`'s entry through `q`. The idiom is `hash((self.x, self.y))`, a tuple of exactly the fields that equality uses.

**Section 5: change a key's fields, and the set loses it.** `p` is in `s`; after `p.x = 99` its hash is different, the set looks where the new hash points, and `p in s` is `False`. `p in list(s)` is `True`, because a list compares with `==` and never asks for a hash, so the object is still in the set's storage. Set `p.x` back to `1` and `p in s` is `True` again. Nothing was removed and nothing was corrupted; the set simply looked in the wrong place, and it will go on looking there for as long as the fields differ. That is why a hashable object should not change, and why the dataclass rules in the next section are what they are.

**Section 6: what `@dataclass` decides for you.** With the defaults, `eq=True` and not frozen, a dataclass gets a field-wise `__eq__` and `__hash__ = None`, which is section 2 done deliberately. `frozen=True` makes the fields read-only and then hashes them, which is section 4 with section 5 ruled out. `eq=False` keeps `object`'s identity for both, which is section 1. There is also `unsafe_hash=True`, which writes a field hash on a class that can still change, and the name says what it is.

**Section 7: `==` is two questions.** `Metres.__eq__` returns `NotImplemented` for anything that is not a `Metres`, and that is not an answer, it is a pass. Python then asks the other operand, and when both sides pass it falls back to identity, so `Metres(1) == 1` is `False` rather than an error, and `1 == Metres(1)` is `False` by the same route with the questions in the other order: `int` passes first, then `Metres` is asked. `!=` is derived from `__eq__`, so `Metres(1) != Metres(1)` is `False` without a `__ne__` being written. [`is` is not `==`](../../04_Names_and_Objects/is_is_not_equals/README.md) is that dispatch on its own.

## If you are coming from Rust

Rust keeps the two as separate derives, `PartialEq` and `Hash`, and its containers demand both: a `HashSet<T>` needs `T: Eq + Hash`, so a type with neither is refused at compile time where Python refuses at run time in section 2. Nothing in the compiler checks that a hand-written `PartialEq` agrees with a derived `Hash`, but the documentation states the same promise and clippy warns on that exact combination, which is the section 3 mistake caught by a lint. Section 5 cannot be written: a value inside a `HashSet` cannot be mutated through the set. The Rust library's [Comparison traits ↗](https://masiarek.github.io/rust-learning-library/12_Traits/comparison_traits/index.html) and [The `HashSet` ↗](https://masiarek.github.io/rust-learning-library/26_Collections/the_hashset/index.html) are the two sides.

## If you are coming from C

C has no operators to overload and no hash table in the language. A table you write takes an equality function and a hash function as a pair, and keeping them consistent is your job and nobody checks. Python's rule in section 2 is the language doing that job for you, by removing the half of the pair that stopped matching.

## If you are coming from ABAP

A hashed or sorted internal table declares its key columns, and both "equal" and "hash" are those columns by construction, so there is no way to define one without the other and the section 3 state cannot arise. ABAP also forbids section 5 outright: the key fields of a row in a hashed table cannot be changed in place, and a `MODIFY` that tries is an error. Python allows the change and loses the object instead, which is the trade this page is about. *(Not machine-checked — CI cannot run ABAP.)*

## Try it

1. **Search a codebase you maintain for `def __eq__`** and, for each class, check whether `def __hash__` is beside it and whether instances are ever put in a set, used as dict keys, or passed to a function under `functools.lru_cache`, which hashes its arguments.
2. **Find a `@dataclass` that is used as a dict key.** If it is not `frozen=True`, work out how it ever worked.
3. **Put an object of yours in a set, change one of the fields its `__eq__` compares, and test membership**, then change the field back. Section 5 says it comes and goes.
4. **Give a class of yours an `__eq__` that returns `NotImplemented` for foreign types**, and compare an instance against `None`, against an `int` and against an instance of an unrelated class. None of the three should raise.
5. **Sort a list of your objects with `sorted()`**. If it raises `TypeError`, your class has `__eq__` and no ordering, which is the same design decision one operator over.
