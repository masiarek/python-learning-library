# Assignment does not copy

**Level:** 201 · for Python programmers, especially ones coming from C or ABAP

**One line:** `b = a` gives the object a second name and copies nothing, so a change made through either name shows through both — which is why `[[0] * 3] * 3` is one row three times, why a copy made with `[:]` still shares its inner lists, and why a function can change the list you passed it.

```python
a = [1, 2]
b = a
b.append(3)
a           # [1, 2, 3]
a is b      # True
```

A name in Python is an entry in a namespace that points at an object. It has no type, no size and no storage of its own; the object has all three. So `b = a` cannot copy anything, because there is nothing on the left to copy *into*: it writes a second entry pointing at the same object. C copies the bytes of a struct on `=`, and ABAP copies the value of an internal table. Python has no version of that assignment at all. Every `=`, every argument passed to a function and every element put into a container is the pointer case.

Most of the time nothing shows, and that is why the wrong model survives so long. An `int`, a `str`, a `tuple` or a `bytes` object cannot change after it is made, so two names for one of them are indistinguishable from two copies. The rule only becomes visible when the shared object is a `list`, a `dict`, a `set`, a `bytearray` or an instance of a class you wrote, and someone changes it through one of its names.

## What the run shows

**Section 1: two names, one list.** `b.append(3)` changes the list, and `a` names that same list, so `a` shows the change. `a is b` is `True` because there is one object. Nothing was copied at `b = a`, and nothing could have been.

**Section 2: rebinding is not mutating.** `b = b + [4]` looks like the same kind of statement as `b.append(3)`, and it is the opposite: `+` builds a new list, and `=` points `b` at it. `a` keeps the old list and `a is b` is now `False`. The four `int` rows are why people meet this rule late. `m += 1` cannot change the object `1`, so it rebinds `m` to a new `int`, and `n` is untouched; with objects that cannot change, sharing has no consequences. [`+=` is not `+`](../plus_equals_is_not_plus/README.md) is about the same statement when the object *can* change.

**Section 3: the grid that is one row, three times.** `[[0] * 3] * 3` runs the inner `[0] * 3` once, which makes one list, and then the outer `* 3` repeats the *reference* to it. `grid[0] is grid[1]` is `True`, so setting `grid[0][0]` sets the only row there is. The comprehension runs `[0] * 3` on each of its three iterations, so `rows` holds three lists. The same trap is in `[[]] * n`, `[{}] * n` and `dict.fromkeys(keys, [])`, which gives every key the one list.

**Section 4: a copy is one level deep.** `a[:]` builds a new outer list whose elements are the very same inner lists: `a is b` is `False` and `a[0] is b[0]` is `True`. That is a *shallow* copy, and the table shows that every idiom for copying a list makes one: `a[:]`, `list(a)`, `a.copy()`, `copy.copy(a)`, `sorted(a)`, `a * 2`, `[*a]`. Only `copy.deepcopy` copies what the elements point at. `dict(d)` and `d.copy()` are shallow in the same way. A shallow copy is a complete copy whenever the elements are objects that cannot change, which is the usual case: a list of numbers or strings. It is the nested list and the dict of lists where the inside is still shared.

**Section 5: a call is an assignment.** Passing `data` to `grow` binds the parameter name `lst` to the caller's list, the way `b = a` did in section 1. `lst.append(0)` therefore changes the caller's list. `regrow` builds a new list and binds its *local* name to it, and the caller sees nothing, because rebinding a name never affects the other names of the object it used to point at. Python's convention is neither pass-by-value, since the list was not copied, nor pass-by-reference, since `regrow` could not rebind the caller's `data`. A function that means to change the caller's list mutates it; one that means not to copies first.

**Section 6: an immutable container, with mutable contents.** `t[1] = 'y'` raises `TypeError`, because a tuple's slots cannot be reassigned. `t[0].append(1)` succeeds, because it changes the list, not the tuple: `t` still holds the same list, which now has one element. That is also why `hash(t)` raises. A tuple is hashable only when every element is, and a list is not, so a tuple with a list inside cannot be a dictionary key or a set member.

## If you are coming from C

`b = a` on two structs copies every byte, and on two pointers copies the address. Python names are always the second kind, and there is no first kind: no declaration puts a list "in" `b`, so no assignment can copy one there. Asking for a copy is a call, `list(a)` or `copy.deepcopy(a)`, and section 4 says how deep each one goes. There is also no `&` to warn you that sharing is about to start. It starts at every assignment, every call and every insertion into a container, and the only way to know whether it matters is to know whether the object can change.

## If you are coming from Rust

Rust decides the same question by type. `let b = a;` copies a `Copy` type such as an `i32` and *moves* anything else, after which `a` is gone and using it is `E0382`. Two live names for one heap object take `Rc` or `Arc`, and changing it through them takes `RefCell` or a `Mutex`, so the compiler always knows who may write. Python has only the shared case and no compiler tracking it: the discipline the borrow checker enforces is yours to keep. The Rust library's [Copy or move ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/copy_or_move/index.html) is the fork Python does not have, and [A name is not a place ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/a_name_is_not_a_place/index.html) is the half of the model the two languages share.

## If you are coming from ABAP

ABAP assignment is by value. `lt_b = lt_a` gives `lt_b` its own internal table, and a later `APPEND` to one is invisible through the other; the runtime may share the storage until the first write, but that is an optimisation that keeps the value semantics, not a change to them. Sharing has to be asked for, with a data reference (`REF TO`), a field symbol (`ASSIGN`) or a `CHANGING` parameter, and an `IMPORTING` parameter cannot be written to at all. So ABAP has both kinds of assignment and chooses at the declaration. Python has one kind, a function may change any argument it receives, and whether that matters depends on the object rather than on the signature. *(Not machine-checked — CI cannot run ABAP.)*

## Try it

1. **Search a codebase you maintain for a list literal multiplied by a count**: `grep -rn '\] \* ' --include='*.py'`. For each hit, ask what the repeated element is. `[0] * n` is fine; `[[]] * n` and `[{}] * n` are section 3.
2. **Take a function of yours that receives a list or a dict**, call it with `copy.deepcopy(arg)` as well as with `arg`, and compare the two arguments afterwards with `==`. If they differ, the function mutates its input, and every caller shares that.
3. **Find a `.copy()` or `[:]` in your code whose elements are lists or dicts.** Change one element through the copy and print the original. Section 4 says which idiom would have protected it.
4. **Run `d = dict.fromkeys(['a', 'b'], [])` and append to `d['a']`.** Write down what `d['b']` will be before you look.
5. **Look for a function that returns a list or dict it also keeps**, such as a cache or a module-level default. A caller that appends to the result is appending to your cache.
